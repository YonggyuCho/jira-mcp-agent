# 웹 화면

에이전트의 실행 결과를 브라우저로 보고, 버튼으로 미리보기·발송을 하는 화면.
사용자가 "다시 보내봐", "리스트 뽑아줘", "보낸 거야?" 를 Claude 에게 매번 묻지 않아도 되게 하려고 만들었다.

조직 특정 값(도메인, IP, 누가 쓰는지)은 `docs/internal/WORKING-RULES.md` 6장과 `HANDOFF.md` 에 있다.
설치 절차는 `DEPLOYMENT.md` 의 "웹 화면" 절.

---

## 1. 구조

```
cron (평일 09:00) ─┐
                   ├─▶ python -m agent.daily ─▶ runs/<날짜>/<시각>-<출처>.json ─▶ Teams 웹훅
웹 버튼 ───────────┘           (판정)                  (실행 기록)
                                                          │
브라우저 ─ HTTPS ─▶ nginx :443 ─▶ 127.0.0.1:8090  web.server ─ 읽어서 표시
```

| 파일 | 역할 |
|---|---|
| `agent/store.py` | 실행마다 결과를 JSON 으로 저장. 성공·실패 모두. 웹·이력·"이전 대비" 의 원천 |
| `agent/daily.py` | `--trigger cron/web/manual` 로 출처를 남긴다. 기록 저장 실패는 종료 코드에 영향 없음 |
| `web/server.py` | 화면 서버 (v2). **표준 라이브러리만** 쓴다. 판정 결과를 JSON 으로 만들어 템플릿에 넣는다 |
| `web/templates/app.html` | **화면 모양 전부** — Claude 디자인 목업을 옮긴 것. CSS·JS 인라인, 외부 리소스 없음. 서버는 `/*__DATA__*/null` 자리에 JSON 만 넣는다 |
| `web/server_v1.py` | **백업** — 디자인 개편 전 화면 (서버가 HTML 을 직접 만들던 판) |
| `web/__main__.py` | `python -m web` — `.env` 의 `WEB_UI` 로 판을 고른다. 기본 v2, `WEB_UI=v1` 이면 백업 |
| `runs/` | 실행 기록. 이슈 키·담당자 이름이 있어 **`.gitignore` 로 제외** |

### 깨면 안 되는 것

1. **웹은 판정하지 않는다.** 버튼은 cron 과 똑같은 `python -m agent.daily` 를 subprocess 로 실행한다.
   그래서 웹에서 본 결과와 아침 리포트가 항상 같다. 판정 규칙은 `agent/collect.py` `_judge()` 한 곳.
2. **미리보기는 절대 보내지 않는다.** `AGENT_DRY_RUN=1` 을 강제로 넣어 실행한다.
3. **앱은 `127.0.0.1` 에만 묶는다.** 밖에서 직접 못 붙는다. HTTPS 는 nginx 가 맡는다.
4. **버튼(POST)은 같은 출처만 받는다** (CSRF 방지). 처리 후 303 으로 결과 화면에 보낸다 —
   새로고침해도 다시 발송되지 않게.
5. 발송·미리보기는 동시에 하나만 (잠금).

## 2. 화면

| 경로 | 내용 |
|---|---|
| `/` | **현황** 탭 (10-15 "오늘" → "현황") — 가장 최근 결과. 건수(위험·불일치·정상·전체), **이전 날짜 리포트와 비교** (새로 생긴 문제 / 해결된 문제), 버튼 2개, 표. 키 옆 💬 = 댓글 |
| `/comments?key=` | 이슈 댓글 최근 30개 (읽기 토큰) — 허용 범위 밖이면 `ok:false` |
| `POST /action/comment` | **댓글 달기** — `WEB_COMMENT_ENABLED=1` 일 때만, 쓰기 토큰. `{key, text}` |
| `/runs` | 실행 기록 — 자동·웹·수동, 성공·실패, 웹훅 응답, 오류 메시지 |
| `/run/<날짜>/<파일>` | 특정 실행 하나 |
| `/create` | **Jira 등록 (데모)** — 상위 선택 + 매번 바뀌는 값만 입력, 고정값은 자동. 보낼 JSON 미리보기. **실제 등록은 안 함** |
| `POST /action/create` | **실제 등록** — `WEB_CREATE_ENABLED=1` 일 때만. 허용 범위 재확인 + 직전 Dry-run 후 1~4단계 실행 |
| `POST /action/validate` | 등록 검증 (dry-run) — 읽기 API 로 각 단계 통과 여부 확인, 결과 JSON |
| `/create?refresh=1` | 등록 양식을 Jira 에서 다시 읽기 (평소엔 캐시를 바로 보여 주고, 10분 지났으면 뒤에서 다시 읽는다. 이 버튼만 기다린다 — 약 5초) |
| `/healthz` | 살아 있는지 (`ok`) |
| `POST /action/preview` | Jira 새로 읽기, 발송 안 함 |
| `POST /action/send` | 실제 Teams 발송 (확인 창) |

### 표

열: **판정 · Epic · 프로젝트 · 키 · 제목 · 유형 · 상태 · 담당 · 기한 · 일정 준수 · 이유**

- **Epic / 프로젝트 (계층 2단)**: 이슈마다 위로 올라가 Epic 제목과 그 바로 아래 프로젝트·구축 제목을 따로 적는다
  (키 없이 제목만). 프로젝트·구축 이슈 자신은 프로젝트 칸에 자기 제목. Epic 은 보라 글씨, 프로젝트는 짙은 초록 글씨, 묶기는 **프로젝트별**.
  계산은 `agent/collect.py` 의 `lineage`. 예전 기록(필드 없음)은 바로 위 제목을 프로젝트로 본다.
- **제목은 굵게** — 가장 중요한 열.
- 색: 🔴 위험 = 빨강, 🟠 불일치 = 주황, ✅ 정상 = 초록. 이유 글자도 같은 색.
- **엑셀식**: 머리글 클릭 = 정렬(▲▼). 머리글 아래 = 열별 필터 —
  값 열(판정·상위·유형·상태·담당·일정 준수)은 **체크박스 다중 선택**, 키·제목·이유는 글자 포함.
  상단 전체 검색, "보이는 건수 / 전체".
- 🆕 = 이전 리포트에는 없던 걸림.

### 주의

- **웹훅 202 는 Teams 가 받았다는 뜻일 뿐**이다. 채팅 게시 성공·실패는 Power Automate 실행 기록에만 남는다.
  실행 기록 화면의 "발송" 이 곧 "도착" 은 아니다.
- 상위 제목(`parent_title`)은 2026-10-08 이후 기록에만 있다. 그 전 기록은 "-".

### 화면 판 바꾸기 (되돌리기)

사용자가 "예전 화면으로" 라고 하면 **Claude 가 직접** 한다 (사용자 지시).

```bash
echo 'WEB_UI=v1' >> /opt/jira-mcp/.env && sudo systemctl restart gpu-live-web   # 예전 화면
sed -i '/^WEB_UI=/d' /opt/jira-mcp/.env && sudo systemctl restart gpu-live-web  # 새 화면
```

디자인만 바꿀 때는 `web/templates/app.html` 만 고친다. 데이터 모양(`DATA.report.rows[]` 등)은
`web/server.py` 의 `_report()` 가 정한다 — 템플릿과 같이 맞춘다.

### Jira 등록 (데모) — `/create`

목적: Jira 화면에 매번 들어가 필드를 다 채우지 않고, **상위(Epic)만 고르고 매번 바뀌는 값만** 넣어 등록.
지금은 **데모** — 보낼 JSON 을 보여 줄 뿐 Jira 로 보내지 않는다. 토큰도 읽기 전용이다.

`web/jira_form.py` 가 Jira 를 실측해 양식을 만든다 (캐시. 서버 기동 때 미리 읽고, 10분 지나면 화면을 막지 않고 뒤에서 갱신한다. 독립 호출은 동시에 보낸다):
- 유형 id 는 `createmeta` 로 찾는다. 이 사이트는 '회의' 유형이 둘(일반·하위)이라 **하위(subtask) 쪽**을 고른다.
- 상위 후보 = 에픽(`AGENT_EPIC`) 직속 프로젝트·구축. 고르면 기본 유형(프로젝트→하위 작업, 구축→기술지원)·권역·고객사명·요청 경로가 따라온다.
- 사람 목록 = 대상 이슈에 담당·보고·엔지니어·참조로 나온 사람, 많이 나온 순. 엔지니어 기본값 = 가장 흔한 조합.
- 고정값 = 실측에서 100% 같은 값(솔루션·지원 방법·우선순위), 이슈 분류는 판정 규칙과 같은 규칙으로 자동.

| 구분 | 필드 |
|---|---|
| 입력 | **등록 방식**(등록만 / 진행 중까지 / 종료까지 — 기본), 유형, 제목, 담당자, **이슈 분류**(기본값 = 자동 규칙, 바꿀 수 있음 — 바꾸면 리포트 불일치 경고), 시작/Actual Start(날짜+시각 → 시작 날짜·Actual start 둘 다), 기한, 엔지니어(회의는 참조), 설명 |
| 입력 (종료까지) | Actual End(날짜+시각), 일정 준수 여부(종료일·기한으로 자동 추천, 사람이 바꾸면 그 값 유지), Delayed 면 지연 사유 |
| 고정·자동 | 프로젝트, 상위, 솔루션, 엔지니어 지원 방법, **요청 경로(고객 고정)**, 고객사명(통합키), 권역, 우선순위, **보고자** — `.env` `WEB_FORM_REPORTER` 로 고정. 단 기술지원은 화면에 보고자 칸이 없어 만든 사람(토큰 계정)이 된다 (`JIRA-FIELDS.md`) |

미리보기는 등록 방식에 따라 **보낼 요청을 단계별로**(1 등록 → 2 진행 중 → 3 종료 → 4 실제 값 다시 넣기) 보여 준다.

"등록 전 검사" 는 매일 리포트의 미기입 규칙과 같은 항목을 본다 — 이 화면으로 만든 이슈는 리포트에 안 걸리게.

**등록 + 진행 중 + 종료를 한 번에 (실측 결과, 2026-10-08):** 가능하다. 단 순서가 중요하다 —
전환이 Actual start/end 를 '지금 시각' 으로 덮어쓰므로 실제 날짜는 **마지막에** 넣는다 (`JIRA-FIELDS.md` 7장).

```
1. POST /issue                    등록 (상태 = 미해결)
2. POST /issue/<키>/transitions   {"transition":{"id":"2"}}  작업 시작 → 진행 중  (Actual start = 지금 으로 덮임)
3. POST /issue/<키>/transitions   {"transition":{"id":"3"}}  종결 → 종료         (Actual end = 지금 으로 덮임)
4. PUT  /issue/<키>               Actual start / Actual end / 일정 준수 여부 를 실제 값으로
```

중간에 실패하면 이슈는 이미 만들어진 상태라, 화면에 키와 어디까지 됐는지를 보여 줘야 한다.

**등록 흐름:** [등록] → ① 화면 검사(빈 칸이면 창 없이 알림) → ② **Dry-run 자동 실행** → ③ 결과 창에서 등록 여부를 다시 묻는다.
창 구성 (10-15 정리): 등록할 내용 요약(제목·상위·유형·처리) → Dry-run 한 줄 결론 → **단계마다 한 줄**
(1. 이슈 만들기 / 2. 진행 중으로 바꾸기 / 3. 종료로 바꾸기 / 4. 실제 시작·종료 시각 다시 넣기 / 매일 점검 미리보기) → 무엇이 실행되는지 한 줄.
통과면 [취소]/[등록], 미리 확인 못 한 단계가 있으면 [그래도 등록], 실패면 막힌 곳만 + [닫기] (등록 불가).
따로 있던 '검증' 버튼은 없앴다 (10-08 사용자 요구).

**검증 (dry-run) — `POST /action/validate`:** Jira 에는 등록을 미리 시험하는 API 가 없어서, 읽기 API 로
실제 등록 때 실패할 지점을 하나씩 확인한다. 아무것도 쓰지 않는다 (`web/jira_form.py` 의 `validate()`).

| 단계 | 확인 |
|---|---|
| 1. 등록 | 보낼 필드가 그 유형의 등록 화면(createmeta)에 있는지, 필수 필드, 선택값 허용 목록, 사람이 프로젝트에 배정 가능한지(`/user/assignable/search`), 상위 존재·유형 |
| 2·3. 전환 | 같은 유형의 미해결(2)·진행 중(3) 표본 이슈에서 '지금 할 수 있는 전환' 을 조회해 전환 id 존재, 전환 때 필수 입력 없음. **같은 유형에 그 상태 이슈가 없으면**(회의는 바로 종료돼 0건, 10-12 실측) 상태 목록(`/project/{p}/statuses`)이 완전히 같은 다른 등록 유형(하위 작업)의 표본으로 확인하고 그렇게 적는다. **3단계 표본은 범주가 아니라 2단계 전환이 도착하는 상태(진행 중) 그대로** 고른다 — 같은 '진행' 범주인 Pending 에는 종료 전환이 없어 '전환(id 3)이 없음' 오탐이 났다 (10-22). 4단계도 3단계 도착 상태(종료, 취소 아님)로 고른다. 회의 실제 등록에서 전환 2·3 동작 확인 전이라 이 대체는 [추정] 근거 |
| 4. 수정 | 같은 상태(종료)의 표본 이슈 `editmeta` 에 다시 넣을 필드가 있는지 — 종료 상태에서 수정이 막혀 있으면 여기서 잡힌다 |
| 매일 점검 미리보기 | 등록된 셈 치고 `collect._judge()` 에 돌려 내일 리포트에 잡힐지 |

2026-10-08 확인: 정상 요청은 전 단계 통과, 틀린 요청(필수 누락·없는 선택값·설명 공란)은 전부 잡음.
한계: 실제 등록 시점의 권한·자동화 규칙(post function) 차이까지는 못 본다 — 첫 실제 등록은 사람이 결과를 확인한다.
**첫 실제 등록 (2026-10-15, 기술지원, 종료까지):** 4단계 모두 성공. 변경 이력상 전환이 Actual start/end 를 '지금' 으로 덮었다가
4단계에서 입력값으로 되돌아감, 일정 준수 Not Evaluated → On Time, 같은 시간대 다른 이슈·상위 변경 없음, 매일 점검 판정 0건.

**쓰기 토큰 확인법 (아무것도 안 만든다):** 그 토큰으로 `POST /issue` 에 `{"fields":{}}` 를 보낸다.
400(필수값 없음) = 쓰기 범위 있음, 401/403 = 없음. 필수값이 없으니 이슈는 생기지 않는다.

**실제 등록 (2026-10-12 켬) — `POST /action/create`:** `.env` 의 `WEB_CREATE_ENABLED=1` + `JIRA_API_TOKEN_WRITE`.
- 화면 요청을 그대로 믿지 않는다 — 서버가 다시 확인: 프로젝트 = `AGENT_PROJECT`, 유형 = 양식의 3개, 상위 = 에픽 직속 프로젝트·구축,
  전환 = 2·3 만, 마지막 PUT 은 Actual start/end·일정 준수·지연 사유 4개 필드만.
- 보내기 직전 서버가 Dry-run 을 한 번 더 돌리고 실패하면 보내지 않는다.
- 단계마다 결과를 모아 화면에 보여 준다. 중간 실패면 "일부만 처리됨 — 키는 만들어졌음" 과 어디까지 됐는지.
- 기록: `runs/creates.jsonl` → 실행 기록 탭의 "Jira 등록 기록".
- 공용 클라이언트에 `put` 을 추가하지 않았다 (MCP 서버는 읽기 전용 유지) — `request("PUT", …)` 를 등록 코드 안에서만 쓴다.
- 끄기: `.env` 에서 `WEB_CREATE_ENABLED` 를 비우고 서비스 재시작 → 데모로 돌아간다.

2026-10-12 확인: 꺼진 상태 거부, 에픽 밖 상위·허용 안 된 전환·다른 출처 요청 모두 쓰기 전에 거부, 그사이 생성 0건.

### 댓글 — 현황 페이지 💬 (2026-10-15)

표의 키 옆 💬 → 창에서 기존 댓글(최신순 30개)을 보고 새 댓글을 쓴다. [댓글 달기] → **확인 한 줄을 한 번 더 보여 주고** [달기] 해야 올라간다.

- 허용 범위는 서버가 다시 확인 (`web/jira_comment.py`): 프로젝트 = `AGENT_PROJECT` 이고, 솔루션에 `AGENT_SOLUTION` 이 있거나
  **가장 최근 리포트 표에 나온 이슈** (에픽 아래인데 솔루션이 틀린 불일치 이슈에도 달 수 있게). 키 형식이 아니면 거절.
- 작성자는 쓰기 토큰 계정. **@ 알림(멘션)은 넣지 않는다** — 평문만 ADF 문단으로 보낸다 (빈 줄 = 문단, 줄바꿈 = hardBreak). 5000자 제한.
- 수정·삭제는 웹에 없다 — Jira 에서.
- 기록: `runs/comments.jsonl` (시각·키·제목·성공 여부·댓글 id·앞 200자). 저장소에 안 올라간다.
- 끄기: `.env` 의 `WEB_COMMENT_ENABLED` 비우기 → 보기만 된다.
- 쓰기 토큰 범위: **첫 실제 댓글 (2026-10-15, 등록 테스트 이슈) 성공** — 줄바꿈 hardBreak 그대로, 이슈 상태·필드 변경 없음.
- 글 속 주소(http/https)는 링크로 만든다 — API 로 넣은 평문은 Jira 가 자동으로 링크를 걸지 않는다. 웹의 댓글 목록에서도 링크로 보인다.

### 사진 붙여넣기 — 댓글·설명 (2026-10-15)

입력칸에 **Ctrl+V** 로 캡처를 붙이면 커서 자리에 `[사진 n]` 이 들어가고 아래에 미리보기(× 로 빼기)가 생긴다.
보낼 때 서버(`web/jira_media.py`)가:

1. 그 이슈에 첨부로 올린다 — `POST /issue/{key}/attachments` (multipart, `X-Atlassian-Token: no-check`). 파일 이름 `paste-<시각>-<n>-<임의>.png`
2. `GET /attachment/content/{id}` 를 **리다이렉트를 따라가지 않고** 보내 `Location` 의 `…/file/<UUID>/binary` 에서 media UUID 를 꺼낸다
   (2026-10-15 실측 — Jira 화면에서 붙여넣은 사진의 ADF media id 와 같은 값)
3. 본문 ADF 의 `[사진 n]` 자리에 `mediaSingle > media{type:file, id:UUID, collection:""}` 를 넣는다. 자리 표시를 지운 사진은 맨 끝

- **"첨부 없이" 는 Jira 구조상 불가** — 본문은 첨부를 가리킬 뿐이다 (Jira 화면에서 붙여도 같다). 그래서 이슈 첨부 목록에도 보인다.
- 설명: 이슈를 만든 직후(1단계 바로 뒤) 사진을 올리고 설명을 다시 넣는다. 1단계 설명에는 자리 표시를 뺀 글이 들어간다.
- 제한: 한 번에 5장, 장당 10MB, PNG·JPG·GIF (파일 앞부분으로 판단). 화면·서버 둘 다 확인. Dry-run 에 "사진 N장 (MB)" 줄.
- 요청 크기: 사진이 base64 JSON 으로 와서 nginx `client_max_body_size 80m` + `web/server.py` `MAX_BODY` 를 맞춰 올렸다.
- 실패: 사진 올리기에서 막히면 댓글은 달지 않는다. 이미 올라간 사진은 첨부로 남고 화면에 알린다.
- 쓰기 토큰의 첨부 범위: 없는 이슈에 올리기 시도 → 읽기 토큰은 401(범위 없음), 쓰기 토큰은 범위 통과 (10-15 실측).
- 설명도 이제 서버가 ADF 를 만든다 — 주소는 링크로.

### 진행 중 작업

현황 페이지의 '이전 대비' 바로 아래 카드, 그리고 Teams 리포트의 `■ 진행 중 작업 N건` 단락.
상위 이슈(프로젝트·구축)를 뺀 **진행 중 작업만** 한 줄씩: 기한까지 · 진행 N일째(Actual start, 없으면 시작 날짜부터) · 마지막 수정 후.

**색은 기한 하나로만 정한다** (사용자 10-22 — 처음엔 '7일 변화 없음·14일 진행' 도 색으로 봤으나 바꿈):

| 표시 | 조건 |
|---|---|
| 🔴 | 기한 지남 |
| 🟠 | 기한 오늘·내일 (`SOON_DAYS = 1`) |
| 🟡 | 기한 2일 이상 남음 |
| ⚪ | 기한 없음 |

- 순서는 기한 순 (지난 것 먼저). 카드 제목 오른쪽에 색별 건수.
- **위험·불일치 판정과 별개인 '보기' 다.** 헤드라인(위험 N · 불일치 N), 카드 숫자, '이전 대비' 비교에 영향 없음.
  (🔴 기한 지남은 원래도 위험으로 잡히므로 두 곳에 보인다.)
- 실행 기록 `report.open_tasks` 에 저장된다. 예전 기록에는 없어 카드가 안 나온다.
- **끄기**: `.env` `AGENT_OPEN_TASKS=0` → Teams·웹 둘 다 즉시 숨김 (웹은 재시작 필요: `sudo systemctl restart gpu-live-web`).
  완전 원복은 이 기능 커밋 하나를 `git revert`.

## 3. 운영

```bash
systemctl status gpu-live-web            # 상태
sudo systemctl restart gpu-live-web      # web/server.py 를 고쳤으면 반드시
journalctl -u gpu-live-web -n 50         # 앱 로그 (접근 로그는 nginx)
sudo tail -f /var/log/nginx/access.log   # 접근 로그
sudo nginx -t && sudo systemctl reload nginx   # nginx 설정을 고쳤으면
sudo certbot certificates                # 인증서 만료일
systemctl list-timers certbot.timer      # 자동 갱신 타이머
ls runs/$(date +%F)/                     # 오늘 실행 기록
```

- **agent 쪽(판정·렌더)만 고쳤으면 웹 재시작은 필요 없다.** 버튼이 매번 새 프로세스로 agent 를 실행하고,
  화면은 저장된 JSON 을 읽기 때문이다. 다만 화면에는 **다음 실행부터** 새 규칙이 반영된다 — 바로 보려면 미리보기.
- `web/server.py`·`agent/store.py` 를 고쳤으면 재시작한다 (store 는 웹이 import 한다). `app.html` 은 요청마다 읽으므로 재시작 없이 반영된다.
- 화면을 고친 뒤에는 `curl -s https://<도메인>/ | grep ...` 으로 HTML 이 바뀌었는지 본다.
  **서버에는 브라우저가 없어 클릭·모양 확인은 못 한다** — 사용자 스크린샷으로 확인한다.

### 접근 통제

앱에는 **로그인이 없다.** 접근 통제는 클라우드 보안 그룹(또는 nginx `auth_basic`)으로 한다.
**둘 다 없이 열면 누구나 발송 버튼을 누를 수 있다.**

로그인을 다시 붙이려면 `DEPLOYMENT.md` 의 "웹 화면" 절 — curl 로 확인할 때 `-w %{redirect_url}` 을
쓰면 비밀번호가 출력되는 함정이 있다.
